# 本科毕设系统验收速读指南

适用项目：`misspelling-platform`

适用场景：老师系统验收、毕业设计答辩前 2 小时速读、主机重启后的快速恢复上线。

最后更新：`2026-04-07`

---

## 1. 先背这 10 句话

1. 这是一个“错拼词扩散研究平台”，核心任务是围绕一个标准词及其错拼变体做数据拉取、算法分析、任务管理和结果展示。
2. 系统前端是 `React + Vite + TypeScript + Ant Design`，后端是 `FastAPI + SQLAlchemy + Celery + Redis + MySQL`。
3. 前端页面由 `nginx` 直接托管 `frontend/dist`，`/api/*` 被反向代理到 `127.0.0.1:8000` 的 FastAPI。
4. 长耗时算法不在 HTTP 请求里直接跑，而是先写入 `tasks` 表，再由 `Celery worker` 异步执行。
5. 所有算法共用一个统一数据链路：`GBNC -> time_series/time_series_points -> dataset_builder -> adapter -> artifacts/result_json`。
6. 当前真实使用的数据源是 `GBNC`，`GDELT` 已从当前版本中去掉。
7. 传播仿真算法是本系统最重要的算法，它模拟的是“标准拼写”与“非标准拼写簇”之间的竞争扩散，而不是多个错拼之间彼此竞争。
8. 仿真网络是合成网络，不是还原真实社交账号图；节点表示“潜在语言使用/暴露单元”，边表示“可能的社会影响通道”。
9. 数据库里最关键的几张表是：`tasks`、`task_events`、`task_artifacts`、`time_series`、`time_series_points`、`lexicon_terms`、`users`。
10. 老师如果问“为什么这样设计”，核心回答是：为了让算法任务可追踪、可复现、可部署、可展示，并且保证演示时稳定。

## 3. 系统一句话架构

可以直接这样讲：

> 这个系统是一个基于 GBNC 时间序列语料的错拼研究平台。用户在前端发起算法任务，后端将任务写入数据库并交给 Celery 异步执行，算法运行完成后会把结果、图像和 CSV/JSON 产物持久化，再由前端任务详情页统一展示。

系统运行链路：

```text
浏览器
  -> nginx
     -> 前端静态文件 frontend/dist
     -> /api/* 反代到 FastAPI:8000

FastAPI
  -> task_service 写 tasks/task_events
  -> Celery 异步调度

Celery worker
  -> dataset_builder 构造算法数据集
  -> algorithm adapter 执行算法
  -> artifact_service 写 png/csv/json
  -> tasks.result_json + task_artifacts 持久化

底层支撑
  -> MySQL 存结构化数据
  -> Redis 做 Celery broker/result backend
  -> GBNC 作为主要外部数据源
```

## 8. 统一算法运行链路

系统里四类主要算法的执行流程是一致的，老师如果问“算法任务是怎么跑起来的”，你就答这条主链：

```text
前端页面提交参数
-> FastAPI 路由接收
-> task_service 创建任务并写入 tasks
-> Celery worker 异步执行
-> dataset_builder 从 GBNC/time_series 组装统一数据集
-> 对应 adapter 执行算法
-> artifact_service 写 CSV/JSON/PNG/GIF
-> tasks.result_json / task_artifacts / task_events 更新
-> 前端任务详情页读取并展示
```

这个统一链路是系统设计的关键，因为它让四类算法共用一套任务框架和数据框架。

## 9. 传播仿真算法重点讲解

这一节是验收最重要的部分。

### 9.1 传播仿真到底在模拟什么

当前仿真不是“多个错拼彼此竞争”的模型，而是：

- 标准拼写 `right`
- 非标准拼写簇 `error cluster`

之间的扩散竞争。

也就是说，一个任务只处理：

- 一个标准词
- 若干个该词的错拼变体

但在 ABM 里，多个错拼变体会先被加总成一个“非标准拼写簇”。

这是当前版本最重要的模型边界。

### 9.2 为什么这样设计是合理的

因为你的毕业设计当前回答的问题是：

> 一个词的标准拼写与非标准拼写行为，在群体层面如何竞争、扩散、被纠正和干预？

而不是：

> 多个错拼变体之间谁战胜谁？

这样设计的优点：

- 状态空间更小
- 参数更容易拟合
- 输出更稳定
- 更适合本科阶段系统实现和答辩

### 9.3 仿真输入数据怎么来的

数据链路：

1. 前端提交 `word + variants + start_year + end_year + corpus + smoothing`
2. `dataset_builder.py` 调 `gbnc_data_service.py`
3. 从 GBNC 拉取该词及其变体的年序列
4. 将这批序列持久化到 `time_series` 和 `time_series_points`
5. 仿真再从这批 task 绑定的时间序列构造 `AlgorithmDataset`

### 9.4 仿真数据集怎么构造

位置：`backend/app/algos/simulation_adapter.py`

核心步骤：

- 第一个序列当作标准拼写 `right`
- 其余变体序列加总为 `error`
- `total = right + error`
- `error_share = error / total`
- 对序列做滚动平滑
- 估计 `salience`
- 自动识别 `phase_break`

你可以这样说：

> 传播仿真先把原始时间序列转成标准拼写和非标准拼写簇两条观测曲线，再把它们转成适合 ABM 校准的时间序列特征。

### 9.5 网络是怎么建的

支持的拓扑：

- `grid`
- `watts_strogatz`
- `newman_watts`
- `barabasi_albert`
- `dual_barabasi_albert`

含义：

- `grid`：规则局部传播
- `watts_strogatz/newman_watts`：小世界网络
- `barabasi_albert`：带 hub 的无标度网络

代码位置：

- `_build_graph(...)`
- `NetworkSpellingABM`

### 9.6 节点和状态分别是什么

节点不是现实中的某一个真实账号，而是一个“潜在语言使用/暴露单元”。

状态有三个：

- `unknown`
- `error`
- `right`

你可以这样答：

> 节点代表潜在的写作者或暴露单元，边代表可能的社会影响路径；这是一个合成网络，用来复现群体扩散机制，而不是重建真实社交图。

### 9.7 状态转移机制是什么

仿真中每个时间步会发生这些概率转移：

- `unknown -> error`
- `unknown -> right`
- `error -> right`
- `right -> unknown`
- `right -> error`

影响这些转移的因素主要有：

- `p_self_error`：自发出错
- `p_copy_error`：受邻居错拼影响
- `p_copy_right`：受邻居标准拼写影响
- `p_proofread`：校对纠错
- `p_forget`：遗忘
- `p_norm`：规范压力
- `alpha_salience`：显著性影响
- `beta_phase`：阶段变化增强
- `gamma_hub`：hub 放大效应

### 9.8 参数是怎么拟合出来的

不是手写死的，而是自动搜索拟合。

拟合流程：

1. 先随机采样一批参数
2. 计算模拟曲线与真实曲线差异
3. 选最好的 shortlist
4. 再做局部扰动优化
5. 最后 elite pass 精修

优化目标主要看：

- `right_rmse`
- `error_rmse`
- `share_rmse`
- 峰值偏差
- 峰值时间差
- 尾部偏差
- 稳定性惩罚

### 9.9 仿真输出有什么

主要输出：

- `summary`
- `metrics_summary`
- `best_params`
- `network_summary`
- `variant_breakdown`
- `series_rows`
- `scenario_rows`
- `interventions`

也就是说它不仅给出拟合结果，还会给出：

- 最优参数
- 网络统计
- 干预情景
- 每年的真实/模拟对比

### 9.10 老师如果追问“为什么可信”

你可以答：

> 这个仿真不是为了精确还原某个平台的真实社交网络，而是为了在统一时间序列约束下，用复杂网络和 ABM 方式解释标准拼写与非标准拼写簇的竞争扩散机制。模型通过真实 GBNC 观测曲线进行拟合，输出误差、R²、峰值时间差和干预情景，因此它是“可解释的群体级机制模型”，不是纯粹的黑箱预测。

## 10. 另外三个算法怎么讲

### 10.1 PCMCI 因果网络

核心文件：

- `backend/app/algos/pcmci_adapter.py`

可以这样讲：

> PCMCI 因果网络模块把一个词及其多个变体的年序列对齐成多变量时间序列，然后利用 Tigramite/PCMCI 推断变量之间带时滞的影响关系，输出边、滞后阶数和权重，最后生成可视化网络图。

### 10.2 MRNMR 稳态分析

核心文件：

- `backend/app/algos/mrnmr_adapter.py`

可以这样讲：

> 稳态分析模块围绕 MR 和 NMR 两个指标，衡量错拼强度和规范-错拼关系，并通过密度估计找出稳态点或高密度阶段，用来分析某个词的错拼行为是否进入相对稳定阶段。

### 10.3 DeltaT 偏差

核心文件：

- `backend/app/algos/deltat_adapter.py`

可以这样讲：

> DeltaT 模块先构造标准拼写和总信号曲线，再用 CfC 生成反事实轨迹，并通过 bootstrap 检测实际突变时间和预测突变时间之间的差值，从而量化“偏差”或“滞后”。

### 11.1 最重要的 8 张表

#### `users`

存用户账号。

存所有任务主记录，是系统任务总表。

关键字段可这样记：

- `task_id`
- `task_type`
- `status`
- `params_json`

存任务生命周期日志，例如 `QUEUED / RUNNING / SUCCESS / FAILURE`。

存任务产物索引，例如：

存词项本体。

#### `lexicon_variants`

存词项对应的变体。

#### `time_series`

存一条时间序列的元信息，例如：

- 属于哪个词

- 来自哪个数据源
- 时间窗口是什么

#### `time_series_points`

存真正的时间点和值，是时间序列明细表。

### 11.2 为什么要拆成 `time_series` 和 `time_series_points`

因为时间序列天然是一对多结构：

- 一条序列有元信息
- 一条序列下有很多年点

拆表后更利于：

- 复用
- 查询
- 按 task 绑定
- 给多个算法共享

## 12. Docker 和网站部署怎么讲

### 12.1 容器组成

`docker-compose.yml` 管 5 个服务：

- `mysql`
- `redis`
- `db-init`
- `api`
- `worker`

作用：

- `mysql`：数据库
- `redis`：Celery 队列/结果后端
- `db-init`：初始化 SQL
- `api`：FastAPI 服务
- `worker`：Celery 算法执行器

### 12.2 Dockerfile 怎么讲

位置：

- `backend/Dockerfile`

逻辑很简单：

1. 基于 Python 3.11 镜像
2. 安装 `requirements.txt`
3. 复制 `app/`
4. 用 `uvicorn` 启动 FastAPI

### 12.3 网站为什么能访问

因为线上入口不是直接暴露 Vite，而是：

- `nginx` 托管 `frontend/dist`
- `nginx` 把 `/api/*` 代理到 `127.0.0.1:8000`

Nginx 配置位置：

- `/etc/nginx/sites-available/misspelling-platform`

其中关键点：

- `root /srv/apps/backend/misspelling-platform/frontend/dist;`
- `location /api/ { proxy_pass http://127.0.0.1:8000; }`

### 12.4 主机重启后怎么恢复上线

这是最重要的运维步骤。

```bash
cd /srv/apps/backend/misspelling-platform
docker compose up -d --build

cd /srv/apps/backend/misspelling-platform/frontend
npm run build

nginx -t
systemctl reload nginx
```

### 12.5 我这次实际恢复时做了什么

这次主机重启后，我实际恢复步骤就是：

1. `docker compose up -d --build`
2. 发现 `db-init` 密码写死为 `root`
3. 修复 `docker-compose.yml`，让 `db-init` 和 `mysql` healthcheck 都读取 `.env` 的 `MYSQL_ROOT_PASSWORD`
4. 重建容器
5. 重新 `npm run build`
6. `systemctl reload nginx`
7. 验证：
   - `docker compose ps`
   - `curl http://127.0.0.1:8000/health`
   - `curl -I https://misspelling.online`

### 12.6 线上关键文件

- 部署编排：`docker-compose.yml`
- 后端镜像：`backend/Dockerfile`
- 环境变量：`.env`
- nginx 站点配置：`/etc/nginx/sites-available/misspelling-platform`
- 前端产物目录：`frontend/dist`

## 14. 老师高频问题与回答模板

### Q1：这个系统到底解决什么问题？

答：

> 这个系统围绕“词的标准拼写与错拼行为”构建了一个可部署、可运行、可解释的研究平台。它可以对错拼时间序列进行数据拉取、任务化分析、传播仿真、因果网络、稳态分析和偏差分析，并把结果统一持久化和展示。

### Q2：为什么要用 FastAPI？

答：

> 因为它适合快速构建类型清晰的 REST API，而且和 Pydantic、异步接口、自动文档集成很好，适合毕业设计这种既要开发速度又要接口清晰的项目。

### Q3：为什么要用 Celery？

答：

> 因为算法任务运行时间长、还要生成图和文件，不适合在 HTTP 请求里同步跑。Celery 可以把任务异步化，避免请求超时，同时方便做任务状态跟踪、失败重试和产物管理。

### Q4：为什么要用 MySQL？

答：

> 因为系统里大量内容是结构化数据，包括用户、任务、时间序列、产物、日志、权限和报告，关系型数据库更适合维护这些稳定的数据关系。

### Q5：为什么还要有 Redis？

答：

> Redis 主要是 Celery 的 broker 和 result backend，不是主数据存储。它负责异步任务调度链路。

### Q6：为什么时间序列要落库？

答：

> 因为多个算法都会复用同一批时间序列数据。如果每次都重新拉取和重新对齐，不稳定且浪费时间。落库后可以复用、审计、导出，也方便任务之间共享。

### Q7：传播仿真里的节点是不是现实中的用户？

答：

> 不是。当前版本是合成复杂网络。节点表示潜在的语言使用或暴露单元，边表示可能的社会影响路径。它的目的不是重建真实社交图，而是解释群体层面的扩散机制。

### Q8：为什么传播仿真不是多个错拼互相竞争？

答：

> 当前版本把多个错拼聚合成一个“非标准拼写簇”，重点研究标准拼写与非标准行为之间的竞争。这能降低状态空间复杂度，让模型更稳定，也更符合本科阶段系统实现的目标。

### Q9：传播仿真的参数是拍脑袋设的吗？

答：

> 不是。系统会自动搜索参数，并以真实时间序列为约束，最小化真实曲线和模拟曲线之间的误差，所以参数是通过拟合得到的，不是手工写死的。

### Q10：为什么要用 NetworkX？

答：

> 因为传播仿真本质是复杂网络上的扩散过程，需要方便地构造小世界、无标度等不同拓扑，NetworkX 很适合这类实验性网络建模。

### Q11：为什么 DeltaT 用到了 TensorFlow 和 CfC？

答：

> 因为 DeltaT 模块需要构造反事实预测轨迹，当前版本移植了原 notebook 风格的 CfC 方案，所以依赖 TensorFlow 和 ncps。

### Q12：项目管理和分析中心为什么不见了？

答：

> 这两个模块的后端能力和数据库结构还在，但为了保证当前验收稳定性，前端入口先下线了，当前答辩主线聚焦词分析、传播仿真和三个核心算法模块。

### Q13：为什么 GDELT 没用了？

答：

> 当前版本统一切到了 GBNC 数据链路，GDELT 已不作为实际分析数据源使用。这样数据来源更统一，也更利于维护一套稳定的时间序列算法管线。

### Q14：为什么要用 Docker + nginx？

答：

> Docker 保证部署环境一致，便于重启和恢复；nginx 负责 HTTPS、静态文件托管和 `/api` 反向代理，这样线上结构更清晰，也更接近生产部署方式。

## 15. 当前版本要注意的地方

1. 旧文档里仍有少量历史信息，例如 captcha、旧的项目分析页面、旧数据源说明，不一定完全等于当前 UI。
2. 当前外部核心数据源是 `GBNC`，不是 `GDELT`。
3. `项目管理` 和 `分析中心` 后端代码还在，但前端导航已隐藏，不建议作为本轮验收主展示内容。
4. 传播仿真当前是“标准拼写 vs 非标准拼写簇”模型，这是必须主动说明的模型边界。
5. 主机重启后，记得不仅要起 `docker compose`，还要重新 build 前端并 reload `nginx`。

## 16. 最后给你的应试建议

如果老师开始拷代码，不要试图把整个项目从头讲到尾。你就稳稳抓住下面这条主线：

> 前端提交任务 -> FastAPI 写任务 -> Celery 异步跑算法 -> GBNC 时间序列入库 -> adapter 算法计算 -> 产物生成 -> 前端任务详情展示。

然后把传播仿真单独讲深一点：

> 一个词、一组错拼、统一时间序列、合成网络、三状态扩散、自动参数拟合、输出干预场景。

只要这两条主线讲顺，老师大概率会认为你对系统是熟的。
